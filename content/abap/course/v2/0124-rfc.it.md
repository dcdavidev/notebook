_Livello pro_

Una **remote function call (RFC)** esegue un modulo funzione in un'altra sessione, di solito in un altro sistema SAP. È il modo più vecchio, e ancora il più usato, con cui i sistemi SAP comunicano fra loro: BAPI, ALE, la stessa SAP GUI e i connettori esterni (Java, .NET, Python) usano tutti la RFC. Da ABAP una RFC sembra quasi una normale `CALL FUNCTION`, con una parola in più: `DESTINATION`.

## I moduli funzione abilitati RFC

Solo i moduli funzione con tipo di elaborazione **Modulo abilitato RFC** (in `SE37`, scheda **Attributi**) si possono chiamare via RFC. La loro interfaccia ha alcune regole:

- tutti i parametri sono passati **per valore** (`VALUE(...)`);
- ogni parametro ha un tipo, e il tipo deve essere un tipo del Dizionario o un tipo predefinito, non un tipo di un programma locale;
- niente tipi generici come `any` o `data`, e niente riferimenti;
- gli errori si segnalano con eccezioni classiche (`EXCEPTIONS`); le eccezioni basate su classi sono supportate in RFC solo nei rilasci recenti, quindi le eccezioni classiche restano la scelta sicura.

```abap
FUNCTION z_flight_get_seats.
*"----------------------------------------------------------------------
*"  IMPORTING
*"     VALUE(IV_CARRID) TYPE S_CARR_ID
*"     VALUE(IV_CONNID) TYPE S_CONN_ID
*"     VALUE(IV_FLDATE) TYPE S_DATE
*"  EXPORTING
*"     VALUE(EV_SEATS_FREE) TYPE I
*"  EXCEPTIONS
*"     FLIGHT_NOT_FOUND
*"----------------------------------------------------------------------
  SELECT SINGLE seatsmax - seatsocc FROM sflight
    WHERE carrid = @iv_carrid AND connid = @iv_connid AND fldate = @iv_fldate
    INTO @ev_seats_free.
  IF sy-subrc <> 0.
    RAISE flight_not_found.
  ENDIF.
ENDFUNCTION.
```

Un modulo funzione abilitato RFC è un'API: chiunque abbia l'autorizzazione giusta può chiamarlo dall'esterno. Controlla le autorizzazioni al suo interno con `AUTHORITY-CHECK` (vedi [i controlli di autorizzazione](./0110-authorization-checks.it.md)); il chiamante ha bisogno dell'oggetto di autorizzazione `S_RFC` per il suo gruppo funzione.

## Le destinazioni in SM59

Una **destinazione** dice al sistema dove e come collegarsi. La gestisci in `SM59`:

| Tipo di connessione | Destinazione                                                            |
| ------------------- | ----------------------------------------------------------------------- |
| `3`                 | un altro sistema ABAP: host, numero di sistema, mandante, dati di logon |
| `T`                 | un programma esterno via TCP/IP (server RFC registrato)                 |
| `G` / `H`           | un server HTTP (esterno / ABAP), usato per HTTP, non per RFC            |

Due destinazioni esistono sempre, senza configurazione:

- `NONE`: una nuova sessione nello stesso sistema;
- `BACK`: il sistema che ti ha chiamato, da usare dentro un modulo funzione chiamato via RFC.

In `SM59`, **Test di connessione** verifica la rete e **Logon remoto** verifica l'utente. Una connessione **RFC trusted** permette agli utenti di entrare nel sistema di destinazione con il proprio utente, senza una password salvata.

> [!TIP]
> Una destinazione è un contatto nella rubrica del telefono. Chiami "Magazzino Milano" per nome; il contatto contiene il numero, l'interno e la persona da chiedere. Se il magazzino cambia numero, aggiorni il contatto una volta, non ogni chiamata.

## La RFC sincrona

```abap
DATA lv_seats   TYPE i.
DATA lv_message TYPE c LENGTH 255.

CALL FUNCTION 'Z_FLIGHT_GET_SEATS'
  DESTINATION 'ZFLIGHT_QAS'
  EXPORTING
    iv_carrid             = 'LH'
    iv_connid             = '0400'
    iv_fldate             = '20261215'
  IMPORTING
    ev_seats_free         = lv_seats
  EXCEPTIONS
    flight_not_found      = 1
    system_failure        = 2 MESSAGE lv_message
    communication_failure = 3 MESSAGE lv_message
    OTHERS                = 4.

CASE sy-subrc.
  WHEN 0. WRITE / |Posti liberi: { lv_seats }|.
  WHEN 1. WRITE / 'Volo non trovato'.
  WHEN 2 OR 3. WRITE / |Errore RFC: { lv_message }|.
  WHEN OTHERS. WRITE / 'Errore imprevisto'.
ENDCASE.
```

- Gestisci **sempre** `system_failure` (il programma remoto è andato in dump) e `communication_failure` (la connessione non è riuscita). Senza di loro, qualsiasi problema RFC termina il tuo programma con un dump.
- `MESSAGE` riempie un campo di testo con la descrizione dell'errore.
- Il chiamante aspetta che il modulo funzione remoto finisca.
- La sessione remota resta aperta fino alla fine del tuo programma, o finché non chiami `RFC_CONNECTION_CLOSE`. Per le BAPI è importante: chiama `BAPI_TRANSACTION_COMMIT` sulla stessa destinazione, così gira nella stessa sessione remota della BAPI.

Per controllare il sistema di destinazione, chiama il modulo funzione standard `RFC_SYSTEM_INFO`:

```abap
DATA ls_info TYPE rfcsi.
CALL FUNCTION 'RFC_SYSTEM_INFO'
  DESTINATION 'ZFLIGHT_QAS'
  IMPORTING
    rfcsi_export          = ls_info
  EXCEPTIONS
    system_failure        = 1
    communication_failure = 2
    OTHERS                = 3.
IF sy-subrc = 0.
  WRITE: / ls_info-rfcsysid, ls_info-rfchost, ls_info-rfcdbsys.
ENDIF.
```

## RFC asincrona, transazionale e in coda

| Variante                  | Istruzione                                        | Comportamento                                                   |
| ------------------------- | ------------------------------------------------- | --------------------------------------------------------------- |
| sincrona (sRFC)           | `CALL FUNCTION ... DESTINATION`                   | il chiamante aspetta il risultato                               |
| asincrona (aRFC)          | `CALL FUNCTION ... STARTING NEW TASK`             | il chiamante prosegue; i risultati arrivano in un callback      |
| transazionale (tRFC)      | `CALL FUNCTION ... IN BACKGROUND TASK` (obsoleta) | gira una volta, dopo il `COMMIT WORK`                           |
| RFC in background (bgRFC) | `CALL FUNCTION ... IN BACKGROUND UNIT`            | gira una volta dopo il `COMMIT WORK`, anche in code (in ordine) |

aRFC e bgRFC sono mostrate con il codice in [elaborazione parallela e in background](./0114-parallel-processing.it.md). Nel codice nuovo usa la bgRFC al posto di tRFC e qRFC. Le chiamate tRFC si controllano in `SM58`, le code in uscita in `SMQ1`.

> [!WARNING]
> Una RFC sincrona verso un sistema lento o irraggiungibile blocca il tuo work process fino al timeout. Nei programmi di dialogo l'utente resta bloccato; nei cicli il problema si moltiplica. Non chiamare RFC dentro i cicli quando una sola chiamata con un parametro tabella fa lo stesso lavoro.

> [!CAUTION]
> Non salvare mai un utente di dialogo con un ruolo ampio in una destinazione `SM59`. Chiunque possa usare la destinazione lavora nel sistema di destinazione con quei diritti. Usa un utente tecnico di tipo **Sistema** con solo le autorizzazioni che servono all'interfaccia, oppure la RFC trusted.

## Esercizio

> [!IMPORTANT]
>
> 1. Crea il modulo funzione abilitato RFC `Z_FLIGHT_GET_SEATS`.
> 2. Chiamalo da un report con `DESTINATION 'NONE'`, gestendo tutte le eccezioni.
> 3. Chiamalo con una destinazione che non esiste e guarda `sy-subrc` e il messaggio.

### Soluzione

Con `DESTINATION 'NONE'` la chiamata gira in una nuova sessione dello stesso sistema e restituisce i posti liberi. Con una destinazione sconosciuta, `sy-subrc` vale 3 (`communication_failure`) e `lv_message` dice che la destinazione non esiste. Senza la riga `communication_failure`, il programma finirebbe con un errore a runtime.

> [!NOTE]
>
> - Via RFC si possono chiamare solo moduli funzione abilitati RFC, con parametri passati per valore e tipizzati con tipi globali.
> - Le destinazioni stanno in `SM59`; `NONE` e `BACK` esistono sempre.
> - Gestisci sempre `system_failure` e `communication_failure`, con `MESSAGE` per ottenere il testo.
> - La RFC sincrona aspetta; la aRFC gira in parallelo; la bgRFC gira in modo affidabile dopo il commit e sostituisce tRFC e qRFC.
> - Proteggi i moduli funzione abilitati RFC con controlli di autorizzazione, e usa nelle destinazioni utenti tecnici con diritti minimi.
