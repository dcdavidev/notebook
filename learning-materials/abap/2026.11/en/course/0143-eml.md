_Pro level_

A Fiori app talks to a RAP business object through OData. ABAP code talks to it through the **Entity Manipulation Language** (**EML**): a set of ABAP statements to read, create, change, and delete entity instances, call actions, and save. EML goes through the same behavior as Fiori, so your [validations, determinations, and actions](./0142-rap-validations-determinations-actions.md) run no matter who calls.

You already used EML inside the behavior pool. This lesson shows it from the outside: a class, a report, or a background job that works with the travel business object.

## Derived types and the % components

EML works with **derived types**, generated from the behavior definition. You rarely declare them yourself, because inline declarations do it, but you need to know their special components:

| Component  | Meaning                                                                      |
| ---------- | ---------------------------------------------------------------------------- |
| `%cid`     | a content ID you choose, to refer to an instance that doesn't have a key yet |
| `%cid_ref` | refers to the `%cid` of another instance in the same request                 |
| `%tky`     | the transactional key: key fields plus technical fields such as `%is_draft`  |
| `%key`     | only the key fields                                                          |
| `%control` | which fields are set (`if_abap_behv=>mk-on`); filled by `FIELDS ( ... )`     |
| `%target`  | the child instances in a create by association                               |
| `%param`   | the result of an action                                                      |

The explicit form of a derived type looks like `TYPE TABLE FOR CREATE zr_travel\travel`, `TYPE STRUCTURE FOR READ RESULT zr_travel\booking`, and so on.

## Creating with MODIFY ENTITIES

```abap
CLASS zcl_travel_eml DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_travel_eml IMPLEMENTATION.
  METHOD if_oo_adt_classrun~main.
    MODIFY ENTITIES OF zr_travel
      ENTITY Travel
        CREATE FIELDS ( CustomerID BeginDate EndDate CurrencyCode Description )
        WITH VALUE #( ( %cid         = 'T1'
                        CustomerID   = '000001'
                        BeginDate    = '20250701'
                        EndDate      = '20250714'
                        CurrencyCode = 'EUR'
                        Description  = 'Summer holiday' ) )
        CREATE BY \_Booking FIELDS ( CarrierID ConnectionID FlightDate FlightPrice CurrencyCode )
        WITH VALUE #( ( %cid_ref = 'T1'
                        %target  = VALUE #( ( %cid         = 'B1'
                                              CarrierID    = 'LH'
                                              ConnectionID = '0400'
                                              FlightDate   = '20250701'
                                              FlightPrice  = '650.00'
                                              CurrencyCode = 'EUR' ) ) ) )
      MAPPED   DATA(ls_mapped)
      FAILED   DATA(ls_failed)
      REPORTED DATA(ls_reported).

    IF ls_failed IS NOT INITIAL.
      out->write( 'Create failed' ).
      RETURN.
    ENDIF.

    COMMIT ENTITIES
      RESPONSE OF zr_travel
      FAILED   DATA(ls_commit_failed)
      REPORTED DATA(ls_commit_reported).

    IF sy-subrc = 0.
      out->write( |Travel created: { ls_mapped-travel[ 1 ]-TravelUUID }| ).
    ELSE.
      LOOP AT ls_commit_reported-travel INTO DATA(ls_message).
        out->write( ls_message-%msg->if_message~get_text( ) ).
      ENDLOOP.
    ENDIF.
  ENDMETHOD.
ENDCLASS.
```

- `FIELDS ( ... ) WITH` lists the fields you pass and fills `%control` for you.
- The booking refers to its travel with `%cid_ref = 'T1'`, because the travel has no UUID yet when the statement is written.
- `MAPPED` returns the keys the framework assigned (here the managed UUIDs). `FAILED` lists the instances that couldn't be processed, and `REPORTED` the messages.
- Nothing is in the database until `COMMIT ENTITIES`. That's when the save sequence runs: determinations on save, validations, and the database write. If a validation fails, `sy-subrc` is `4` and the messages are in the `RESPONSE` structures.

## Reading, updating, and calling actions

```abap
    DATA(lv_uuid) = ls_mapped-travel[ 1 ]-TravelUUID.

    READ ENTITIES OF zr_travel
      ENTITY Travel
        FIELDS ( TravelID OverallStatus ) WITH VALUE #( ( TravelUUID = lv_uuid ) )
        RESULT DATA(lt_travels)
      ENTITY Travel BY \_Booking
        ALL FIELDS WITH VALUE #( ( TravelUUID = lv_uuid ) )
        RESULT DATA(lt_bookings)
      FAILED DATA(ls_read_failed).

    MODIFY ENTITIES OF zr_travel
      ENTITY Travel
        UPDATE FIELDS ( Description ) WITH VALUE #( ( TravelUUID = lv_uuid  Description = 'Family holiday' ) )
        EXECUTE acceptTravel FROM VALUE #( ( TravelUUID = lv_uuid ) )
        RESULT DATA(lt_accepted)
      FAILED DATA(ls_upd_failed)
      REPORTED DATA(ls_upd_reported).

    COMMIT ENTITIES.
```

- `READ ENTITIES ... BY \_Booking` follows an association. `ALL FIELDS` reads every field.
- `UPDATE FIELDS` changes only the listed fields; the others keep their values.
- `EXECUTE action FROM` calls an action, and `RESULT` returns what the action declared (`$self`).
- `DELETE FROM VALUE #( ( TravelUUID = lv_uuid ) )` deletes, and with the composition, the bookings go too.

A shorter form exists for one entity: `MODIFY ENTITY zr_travel UPDATE FIELDS ( ... ) WITH ...` and `READ ENTITY zr_travel ...`.

> [!WARNING]
> Never use `COMMIT ENTITIES` or `COMMIT WORK` inside a behavior pool, a determination, or a validation: the framework commits for you, and the runtime raises a short dump. Commit only in the code that **starts** the transaction: your report, class, or job.

## Local mode and privileged access

| Addition            | Where you use it                         | Effect                                                                              |
| ------------------- | ---------------------------------------- | ----------------------------------------------------------------------------------- |
| `IN LOCAL MODE`     | only in the behavior pool of the same BO | skips authorization and feature control checks                                      |
| `PRIVILEGED`        | in any consumer                          | skips the authorization checks, if the behavior definition allows privileged access |
| `ROLLBACK ENTITIES` | in the consumer                          | discards everything in the transactional buffer                                     |

`IN LOCAL MODE` isn't allowed outside the business object's own implementation. A consumer always goes through the full checks, which is exactly what you want.

## Exercise

> [!IMPORTANT]
>
> 1. Create the class `ZCL_TRAVEL_EML` and run it with `F9` to create a travel with one booking.
> 2. Extend it: read the new travel, print its `TravelID` and `OverallStatus`, then accept it and print the status again.
> 3. Create a travel with an end date before the begin date. What do `sy-subrc` and `ls_commit_reported` contain after `COMMIT ENTITIES`?

### Solution

After step 2, `TravelID` has the number from the `setTravelID` determination, and the status goes from `O` to `A`. In step 3, `MODIFY ENTITIES` succeeds, because validations run only on save. `COMMIT ENTITIES` sets `sy-subrc` to `4`, `ls_commit_failed-travel` contains the instance, and `ls_commit_reported-travel` the message from `validateDates`.

> [!NOTE]
>
> - EML reads and changes RAP business objects from ABAP, through the same behavior as Fiori.
> - `MODIFY ENTITIES` creates, updates, deletes, and executes actions; `READ ENTITIES` reads and follows associations.
> - Use `%cid` and `%cid_ref` for instances without a key yet; `MAPPED`, `FAILED`, and `REPORTED` return keys, errors, and messages.
> - Changes stay in the transactional buffer until `COMMIT ENTITIES`, which runs the save sequence.
> - `IN LOCAL MODE` only inside the behavior pool; never commit inside the business object's own code.
