In a **managed** business object, the RAP framework does all the work: it keeps the changes in memory, locks, and writes to the database. That's perfect for new apps on new tables. But many systems already have tested code that creates and changes documents: function modules, BAPIs, and classes that check everything and write several tables. RAP lets you reuse that code instead of rewriting it, with **additional save**, **unmanaged save**, and the fully **unmanaged** implementation type.

## Four ways to save

| Implementation type          | Transactional buffer | Who writes to the database        | Typical use                                       |
| ---------------------------- | -------------------- | --------------------------------- | ------------------------------------------------- |
| managed                      | framework            | framework                         | new apps on new tables                            |
| managed with additional save | framework            | framework, then your code as well | write a log, a change document, or call an API    |
| managed with unmanaged save  | framework            | only your code                    | tables written by an existing API                 |
| unmanaged                    | your code            | your code                         | wrap legacy code that has its own buffer and save |

The **transactional buffer** is the memory where the changes of the current transaction wait until `COMMIT ENTITIES`. With managed types the framework owns it; with unmanaged you own it, usually through the legacy code that already has one.

## Additional save

With `with additional save`, the framework saves the entity as usual, and then calls the method `save_modified` of your saver class with everything that was created, updated, and deleted. Add the keyword after `persistent table`:

```abap
managed implementation in class zbp_r_travel unique;
strict ( 2 );

define behavior for ZR_Travel alias Travel
persistent table ztravel
with additional save
lock master
authorization master ( instance )
etag master LocalLastChangedAt
{
  create;
  update;
  delete;
}
```

The saver is a local class in the behavior pool, generated by the quick fix. Here it writes a simple change log to a table `ztravel_log` (key fields `travel_uuid`, `changed_at`, `change_type`):

```abap
CLASS lsc_zr_travel DEFINITION INHERITING FROM cl_abap_behavior_saver.
  PROTECTED SECTION.
    METHODS save_modified REDEFINITION.
ENDCLASS.

CLASS lsc_zr_travel IMPLEMENTATION.
  METHOD save_modified.
    DATA lt_log TYPE STANDARD TABLE OF ztravel_log WITH EMPTY KEY.
    DATA lv_now TYPE timestampl.

    GET TIME STAMP FIELD lv_now.
    DATA(lv_user) = cl_abap_context_info=>get_user_technical_name( ).

    lt_log = VALUE #( BASE lt_log FOR ls_create IN create-travel
                      ( travel_uuid = ls_create-TravelUUID changed_at = lv_now
                        change_type = 'C' changed_by = lv_user ) ).
    lt_log = VALUE #( BASE lt_log FOR ls_update IN update-travel
                      ( travel_uuid = ls_update-TravelUUID changed_at = lv_now
                        change_type = 'U' changed_by = lv_user ) ).
    lt_log = VALUE #( BASE lt_log FOR ls_delete IN delete-travel
                      ( travel_uuid = ls_delete-TravelUUID changed_at = lv_now
                        change_type = 'D' changed_by = lv_user ) ).

    INSERT ztravel_log FROM TABLE @lt_log.
  ENDMETHOD.
ENDCLASS.
```

- `create-travel`, `update-travel`, and `delete-travel` use the alias of the entity. Created rows contain all fields; updated rows contain only the changed fields, flagged in `%control`; deleted rows contain only the key.
- If you need all the fields of updated rows too, write `with additional save with full data`.
- With `with unmanaged save` instead of `persistent table ... with additional save`, the framework writes nothing, and `save_modified` is the only place where data reaches the database.

## Unmanaged: wrap legacy code

In an **unmanaged** business object you implement every operation yourself. The flight reference scenario contains a legacy API in function group `/DMO/FLIGHT_TRAVEL_API`, with its own buffer: `/DMO/FLIGHT_TRAVEL_CREATE` and `/DMO/FLIGHT_TRAVEL_UPDATE` change the buffer, `/DMO/FLIGHT_TRAVEL_SAVE` writes it, and `/DMO/FLIGHT_TRAVEL_INITIALIZE` clears it. That's exactly the shape RAP expects.

```abap
unmanaged implementation in class zbp_r_travel_u unique;
strict ( 2 );

define behavior for ZR_Travel_U alias Travel
lock master
authorization master ( instance )
etag master LastChangedAt
{
  create;
  update;
  delete;
  field ( readonly ) TravelID, LastChangedAt;
  field ( mandatory ) AgencyID, CustomerID, BeginDate, EndDate;

  mapping for /dmo/travel control /dmo/s_travel_inx
  {
    TravelID      = travel_id;
    AgencyID      = agency_id;
    CustomerID    = customer_id;
    BeginDate     = begin_date;
    EndDate       = end_date;
    BookingFee    = booking_fee;
    TotalPrice    = total_price;
    CurrencyCode  = currency_code;
    Description   = description;
    Status        = status;
    LastChangedAt = lastchangedat;
  }
}
```

The handler class needs a method for each operation, plus `read` and `lock`. Here is `create`; `update`, `delete`, and `read` follow the same pattern with the other function modules:

```abap
CLASS lhc_travel DEFINITION INHERITING FROM cl_abap_behavior_handler.
  PRIVATE SECTION.
    METHODS create FOR MODIFY IMPORTING entities FOR CREATE Travel.
    METHODS update FOR MODIFY IMPORTING entities FOR UPDATE Travel.
    METHODS delete FOR MODIFY IMPORTING keys FOR DELETE Travel.
    METHODS read FOR READ IMPORTING keys FOR READ Travel RESULT result.
    METHODS lock FOR LOCK IMPORTING keys FOR LOCK Travel.
    METHODS get_instance_authorizations FOR INSTANCE AUTHORIZATION
      IMPORTING keys REQUEST requested_authorizations FOR Travel RESULT result.
ENDCLASS.

CLASS lhc_travel IMPLEMENTATION.
  METHOD create.
    DATA ls_travel   TYPE /dmo/travel.
    DATA lt_messages TYPE /dmo/t_message.

    LOOP AT entities INTO DATA(ls_entity).
      CALL FUNCTION '/DMO/FLIGHT_TRAVEL_CREATE'
        EXPORTING
          is_travel   = CORRESPONDING /dmo/s_travel_in( ls_entity MAPPING FROM ENTITY USING CONTROL )
        IMPORTING
          es_travel   = ls_travel
          et_messages = lt_messages.

      IF lt_messages IS INITIAL.
        INSERT VALUE #( %cid = ls_entity-%cid TravelID = ls_travel-travel_id ) INTO TABLE mapped-travel.
      ELSE.
        INSERT VALUE #( %cid = ls_entity-%cid ) INTO TABLE failed-travel.
        LOOP AT lt_messages INTO DATA(ls_message).
          INSERT VALUE #( %cid = ls_entity-%cid
                          %msg = new_message( id       = ls_message-msgid
                                              number   = ls_message-msgno
                                              severity = if_abap_behv_message=>severity-error
                                              v1       = ls_message-msgv1
                                              v2       = ls_message-msgv2 ) )
                 INTO TABLE reported-travel.
        ENDLOOP.
      ENDIF.
    ENDLOOP.
  ENDMETHOD.

  METHOD lock.
    TRY.
        DATA(lo_lock) = cl_abap_lock_object_factory=>get_instance( iv_name = '/DMO/ETRAVEL' ).
      CATCH cx_abap_lock_failure.
        RETURN.
    ENDTRY.
    LOOP AT keys INTO DATA(ls_key).
      TRY.
          lo_lock->enqueue( it_parameter = VALUE #( ( name = 'TRAVEL_ID' value = REF #( ls_key-TravelID ) ) ) ).
        CATCH cx_abap_foreign_lock cx_abap_lock_failure.
          APPEND VALUE #( TravelID = ls_key-TravelID ) TO failed-travel.
      ENDTRY.
    ENDLOOP.
  ENDMETHOD.

  " update, delete, read, and get_instance_authorizations omitted
ENDCLASS.
```

`MAPPING FROM ENTITY` uses the `mapping` in the behavior definition to turn CDS element names into the column names of the legacy structure, and `USING CONTROL` copies only the fields the consumer filled.

The saver class connects the legacy buffer to the RAP save sequence:

```abap
CLASS lsc_zr_travel_u DEFINITION INHERITING FROM cl_abap_behavior_saver.
  PROTECTED SECTION.
    METHODS save REDEFINITION.
    METHODS cleanup REDEFINITION.
ENDCLASS.

CLASS lsc_zr_travel_u IMPLEMENTATION.
  METHOD save.
    CALL FUNCTION '/DMO/FLIGHT_TRAVEL_SAVE'.         " legacy buffer to database
  ENDMETHOD.

  METHOD cleanup.
    CALL FUNCTION '/DMO/FLIGHT_TRAVEL_INITIALIZE'.   " clear the legacy buffer
  ENDMETHOD.
ENDCLASS.
```

The other saver methods are `finalize` (last changes before saving), `check_before_save` (last checks; an error here stops the save), `adjust_numbers` (late numbering), and `cleanup_finalize` (clear the buffer after a failed check).

> [!CAUTION]
> In the save phase, never call `COMMIT WORK` or `ROLLBACK WORK`, and don't call BAPIs that commit internally: the RAP framework commits the whole transaction, and an extra commit breaks the LUW. Call BAPIs that only write in the update task (see [update function modules](./0113-update-task.md)), and do every check in `check_before_save`: after that, `save` must not fail.

> [!TIP]
> Unmanaged RAP is like putting a new shop front on an old workshop. The customers see the same modern counter as in every other shop, but behind the door the same craftsmen keep doing the work their way.

## Exercise

> [!IMPORTANT]
>
> 1. Add `with additional save` to your travel business object and write a change log to a table `ztravel_log` in `save_modified`.
> 2. Change a travel in the Fiori preview and check the new row in `ztravel_log` with the data preview in ADT.
> 3. Explain in one sentence why `save_modified` must not call `COMMIT WORK`.

### Solution

1. Use the behavior definition and saver class above, after creating `ztravel_log` with the fields `travel_uuid`, `changed_at`, `change_type`, and `changed_by`.
2. After **Save**, the log has one row with `change_type = 'U'`.
3. The framework commits the whole RAP transaction at the end of the save sequence: a commit inside it would write part of the data before the rest is saved.

> [!NOTE]
>
> - RAP has four implementation types: managed, managed with additional save, managed with unmanaged save, and unmanaged.
> - `with additional save` lets the framework save first and then calls your `save_modified` with `create`, `update`, and `delete`.
> - Unmanaged means you implement create, update, delete, read, and lock, and you own the transactional buffer.
> - Wrap legacy APIs that already split "change the buffer" from "save the buffer"; map fields with `mapping for` and `MAPPING FROM ENTITY`.
> - Never commit in the save phase, and do all checks in `check_before_save`.
