_Pro level_

A **remote function call (RFC)** runs a function module in another session, usually in another SAP system. It's the oldest and still the most used way for SAP systems to talk to each other: BAPIs, ALE, the SAP GUI itself, and external connectors (Java, .NET, Python) all use RFC. From ABAP, an RFC looks almost like a normal `CALL FUNCTION`, with one extra word: `DESTINATION`.

## Remote-enabled function modules

Only function modules with the processing type **Remote-Enabled Module** (in `SE37`, tab **Attributes**) can be called through RFC. Their interface has some rules:

- all parameters are passed **by value** (`VALUE(...)`);
- every parameter has a type, and the type must be a Dictionary type or a built-in type, not a type from a local program;
- no generic types such as `any` or `data`, and no references;
- errors are reported with classic exceptions (`EXCEPTIONS`); class-based exceptions are supported in RFC only on recent releases, so classic exceptions are still the safe choice.

```abap
FUNCTION z_flight_get_seats.
*"----------------------------------------------------------------------
*"  IMPORTING
*"     VALUE(IV_CARRID) TYPE S_CARR_ID
*"     VALUE(IV_CONNID) TYPE S_CONN_ID
*"     VALUE(IV_FLDATE) TYPE S_DATE
*"  EXPORTING
*"     VALUE(EV_SEATS_FREE) TYPE I
*"  EXCEPTIONS
*"     FLIGHT_NOT_FOUND
*"----------------------------------------------------------------------
  SELECT SINGLE seatsmax - seatsocc FROM sflight
    WHERE carrid = @iv_carrid AND connid = @iv_connid AND fldate = @iv_fldate
    INTO @ev_seats_free.
  IF sy-subrc <> 0.
    RAISE flight_not_found.
  ENDIF.
ENDFUNCTION.
```

A remote-enabled function module is an API: anyone with the right authorization can call it from outside. Check authorizations inside it with `AUTHORITY-CHECK` (see [authorization checks](./0110-authorization-checks.md)), and the caller needs authorization object `S_RFC` for its function group.

## Destinations in SM59

A **destination** tells the system where and how to connect. You maintain it in `SM59`:

| Connection type | Target                                                       |
| --------------- | ------------------------------------------------------------ |
| `3`             | another ABAP system: host, system number, client, logon data |
| `T`             | an external program over TCP/IP (registered RFC server)      |
| `G` / `H`       | an HTTP server (external / ABAP), used for HTTP, not RFC     |

Two destinations always exist without configuration:

- `NONE`: a new session in the same system;
- `BACK`: the system that called you, used inside a function module called via RFC.

In `SM59`, **Connection Test** checks the network and **Remote Logon** checks the user. A **trusted RFC** connection lets users log on to the target with their own user, without a stored password.

> [!TIP]
> A destination is an entry in your phone's contacts. You call "Warehouse Milan" by name; the contact holds the number, the extension, and who to ask for. If the warehouse changes number, you update the contact once, not every call.

## Synchronous RFC

```abap
DATA lv_seats   TYPE i.
DATA lv_message TYPE c LENGTH 255.

CALL FUNCTION 'Z_FLIGHT_GET_SEATS'
  DESTINATION 'ZFLIGHT_QAS'
  EXPORTING
    iv_carrid             = 'LH'
    iv_connid             = '0400'
    iv_fldate             = '20261215'
  IMPORTING
    ev_seats_free         = lv_seats
  EXCEPTIONS
    flight_not_found      = 1
    system_failure        = 2 MESSAGE lv_message
    communication_failure = 3 MESSAGE lv_message
    OTHERS                = 4.

CASE sy-subrc.
  WHEN 0. WRITE / |Free seats: { lv_seats }|.
  WHEN 1. WRITE / 'Flight not found'.
  WHEN 2 OR 3. WRITE / |RFC error: { lv_message }|.
  WHEN OTHERS. WRITE / 'Unexpected error'.
ENDCASE.
```

- **Always** handle `system_failure` (the remote program dumped) and `communication_failure` (the connection failed). Without them, any RFC problem ends your program with a dump.
- `MESSAGE` fills a text field with the error description.
- The caller waits until the remote function module ends.
- The remote session stays open until your program ends, or until you call `RFC_CONNECTION_CLOSE`. That matters for BAPIs: call `BAPI_TRANSACTION_COMMIT` on the same destination so it runs in the same remote session as the BAPI.

To check the target system, call the standard function module `RFC_SYSTEM_INFO`:

```abap
DATA ls_info TYPE rfcsi.
CALL FUNCTION 'RFC_SYSTEM_INFO'
  DESTINATION 'ZFLIGHT_QAS'
  IMPORTING
    rfcsi_export          = ls_info
  EXCEPTIONS
    system_failure        = 1
    communication_failure = 2
    OTHERS                = 3.
IF sy-subrc = 0.
  WRITE: / ls_info-rfcsysid, ls_info-rfchost, ls_info-rfcdbsys.
ENDIF.
```

## Asynchronous, transactional, and queued RFC

| Variant                | Statement                                         | Behavior                                                       |
| ---------------------- | ------------------------------------------------- | -------------------------------------------------------------- |
| synchronous (sRFC)     | `CALL FUNCTION ... DESTINATION`                   | the caller waits for the result                                |
| asynchronous (aRFC)    | `CALL FUNCTION ... STARTING NEW TASK`             | the caller continues; results arrive in a callback             |
| transactional (tRFC)   | `CALL FUNCTION ... IN BACKGROUND TASK` (obsolete) | runs once, after `COMMIT WORK`                                 |
| background RFC (bgRFC) | `CALL FUNCTION ... IN BACKGROUND UNIT`            | runs once after `COMMIT WORK`, optionally in queues (in order) |

aRFC and bgRFC are shown with code in [parallel and background processing](./0114-parallel-processing.md). Use bgRFC instead of tRFC and qRFC in new code. You monitor tRFC calls in `SM58`, and outbound queues in `SMQ1`.

> [!WARNING]
> A synchronous RFC to a slow or unreachable system blocks your work process until the timeout. In dialog programs this freezes the user; in loops it multiplies. Don't call RFCs inside loops when one call with a table parameter does the same job.

> [!CAUTION]
> Never store a dialog user with a broad role in an `SM59` destination. Anyone who can use the destination works in the target system with those rights. Use a technical user of type **System** with only the authorizations the interface needs, or trusted RFC.

## Exercise

> [!IMPORTANT]
>
> 1. Create the remote-enabled function module `Z_FLIGHT_GET_SEATS`.
> 2. Call it from a report with `DESTINATION 'NONE'`, handling all the exceptions.
> 3. Call it with a destination that doesn't exist, and look at `sy-subrc` and the message.

### Solution

With `DESTINATION 'NONE'`, the call runs in a new session of the same system and returns the free seats. With an unknown destination, `sy-subrc` is 3 (`communication_failure`), and `lv_message` says the destination doesn't exist. Without the `communication_failure` line, the program would end with a runtime error.

> [!NOTE]
>
> - Only remote-enabled function modules, with parameters passed by value and typed with global types, can be called through RFC.
> - Destinations live in `SM59`; `NONE` and `BACK` always exist.
> - Always handle `system_failure` and `communication_failure`, with `MESSAGE` to get the text.
> - Synchronous RFC waits; aRFC runs in parallel; bgRFC runs reliably after the commit and replaces tRFC and qRFC.
> - Protect remote-enabled function modules with authorization checks, and use technical users with minimal rights in destinations.
