Every ABAP program has its own memory: if a hundred users run the same report, each one reads the same customizing tables from the database a hundred times. **Shared objects** let you keep objects in the **shared memory** of the application server, where every program on that server can read them without a database access. They're useful for data that's read very often and changes rarely: a catalog of airlines, a set of rules, a parsed configuration file.

## Areas, root classes, and handles

Shared objects use three pieces:

| Piece      | What it is                                                                                        | Where you create it     |
| ---------- | ------------------------------------------------------------------------------------------------- | ----------------------- |
| Area       | a named region of shared memory with its settings (client, lifetime, size)                        | transaction `SHMA`      |
| Root class | a normal global class marked `SHARED MEMORY ENABLED`; its instance is the entry point of the area | `SE24` or ADT           |
| Area class | a class generated by `SHMA`, with the same name as the area; it gives you **area handles**        | generated, never edited |

A program never accesses shared memory directly. It asks the area class for a **handle**, with `attach_for_read`, `attach_for_write`, or `attach_for_update`, works with the root object through the handle, and then releases it with `detach` or `detach_commit`.

The root class holds the data. Here it keeps the airlines from `SCARR`:

```abap
CLASS zcl_carrier_root DEFINITION PUBLIC FINAL CREATE PUBLIC SHARED MEMORY ENABLED.
  PUBLIC SECTION.
    TYPES tt_carriers TYPE SORTED TABLE OF scarr WITH UNIQUE KEY carrid.
    DATA mt_carriers TYPE tt_carriers READ-ONLY.
    METHODS load.
    METHODS get_name IMPORTING iv_carrid      TYPE s_carr_id
                     RETURNING VALUE(rv_name) TYPE s_carrname.
ENDCLASS.

CLASS zcl_carrier_root IMPLEMENTATION.
  METHOD load.
    SELECT * FROM scarr INTO TABLE @mt_carriers.
  ENDMETHOD.

  METHOD get_name.
    rv_name = VALUE #( mt_carriers[ carrid = iv_carrid ]-carrname OPTIONAL ).
  ENDMETHOD.
ENDCLASS.
```

Then, in `SHMA`, create the area `ZCL_CARRIER_AREA`, enter `ZCL_CARRIER_ROOT` as the root class, and save. `SHMA` generates the area class `ZCL_CARRIER_AREA`, with the attribute `root` typed as `REF TO zcl_carrier_root`.

## Write and read an area

A writer attaches for writing, creates the root object **inside** the area with `CREATE OBJECT ... AREA HANDLE`, fills it, sets it as root, and commits:

```abap
REPORT zshm_carrier_write.

DATA lo_root TYPE REF TO zcl_carrier_root.

START-OF-SELECTION.
  TRY.
      DATA(lo_handle) = zcl_carrier_area=>attach_for_write( ).
      CREATE OBJECT lo_root AREA HANDLE lo_handle.   " the object lives in shared memory
      lo_root->load( ).
      lo_handle->set_root( lo_root ).
      lo_handle->detach_commit( ).                   " the new version becomes active
      WRITE / 'Area written'.
    CATCH cx_shm_attach_error INTO DATA(lx_error).
      WRITE / lx_error->get_text( ).
  ENDTRY.
```

A reader attaches for reading and uses the root object through the handle:

```abap
REPORT zshm_carrier_read.

PARAMETERS p_carrid TYPE s_carr_id DEFAULT 'LH'.

START-OF-SELECTION.
  TRY.
      DATA(lo_handle) = zcl_carrier_area=>attach_for_read( ).
      DATA(lv_name) = lo_handle->root->get_name( p_carrid ).
      lo_handle->detach( ).
      WRITE / lv_name.
    CATCH cx_shm_no_active_version.
      WRITE / 'No active version: run ZSHM_CARRIER_WRITE first'.
    CATCH cx_shm_attach_error INTO DATA(lx_error).
      WRITE / lx_error->get_text( ).
  ENDTRY.
```

The area class also has static methods for the whole area, such as `invalidate_area` (mark the data as outdated) and `free_area` (remove it).

> [!WARNING]
> `NEW` can't create an object in shared memory: you need `CREATE OBJECT ... AREA HANDLE`. Objects in the area may reference only other objects in the same area, never objects or data in the memory of your program. Always call `detach` or `detach_commit` when you're done, also in error cases: an open write lock blocks every other writer.

## Versions and locks

Shared objects follow simple rules that keep readers safe:

- Many programs can read an area at the same time, but only one can write it.
- With **versioning** switched on in `SHMA`, a writer builds a new version while readers keep reading the old **active version**. At `detach_commit`, the new version becomes active; readers that are still attached to the old one finish undisturbed, and the old version disappears when the last of them detaches.
- Without versioning, there's only one version, and a writer can't attach while readers are attached.

Instead of writing the area from a report, you can let the system build it on demand. Create a class that implements `if_shm_build_instance`, enter it in `SHMA` as the **area constructor class**, and switch on **automatic area structure**. When a reader finds no active version, the system calls the method `build`:

```abap
CLASS zcl_carrier_loader DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_shm_build_instance.
ENDCLASS.

CLASS zcl_carrier_loader IMPLEMENTATION.
  METHOD if_shm_build_instance~build.
    DATA lo_root TYPE REF TO zcl_carrier_root.
    TRY.
        DATA(lo_handle) = zcl_carrier_area=>attach_for_write( inst_name = inst_name ).
        CREATE OBJECT lo_root AREA HANDLE lo_handle.
        lo_root->load( ).
        lo_handle->set_root( lo_root ).
        lo_handle->detach_commit( ).
      CATCH cx_shm_error INTO DATA(lx_error).
        RAISE EXCEPTION TYPE cx_shm_build_failed EXPORTING previous = lx_error.
    ENDTRY.
  ENDMETHOD.
ENDCLASS.
```

In transaction `SHMM` you can see every area instance, its versions, its size, and the attached readers, and you can invalidate or delete an area by hand.

> [!TIP]
> A shared object area is like the notice board in an office. One person at a time pins up a new sheet, everybody else reads it without taking it away, and while someone prepares the new sheet, people keep reading the old one.

> [!CAUTION]
> Shared memory belongs to one application server instance: each server of the system has its own copy, and all of it is lost when the server restarts. Never keep the only copy of business data there. Shared objects aren't available in ABAP Cloud.

## Exercise

> [!IMPORTANT]
>
> 1. Create the root class `ZCL_CARRIER_ROOT` and the area `ZCL_CARRIER_AREA` in `SHMA`.
> 2. Run `ZSHM_CARRIER_READ` before and after `ZSHM_CARRIER_WRITE`, and compare the results.
> 3. Open `SHMM` and find the area instance and its size.

### Solution

Use the classes and reports above. Before the write, the reader prints "No active version": `attach_for_read` raises `cx_shm_no_active_version`. After the write, it prints the airline name, for example `Lufthansa`. In `SHMM`, the area `ZCL_CARRIER_AREA` shows the instance `$DEFAULT_INSTANCE$` with one active version.

> [!NOTE]
>
> - Shared objects keep objects in the shared memory of the application server, for data read often and changed rarely.
> - An area (`SHMA`) has a root class marked `SHARED MEMORY ENABLED` and a generated area class.
> - Use `attach_for_read` or `attach_for_write`, create objects with `CREATE OBJECT ... AREA HANDLE`, and always `detach` or `detach_commit`.
> - One writer and many readers; readers keep the active version while a new one is built.
> - Shared memory is per server and lost on restart; monitor it in `SHMM`.
