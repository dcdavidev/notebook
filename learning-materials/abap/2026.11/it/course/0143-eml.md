Un'app Fiori parla con un business object RAP tramite OData. Il codice ABAP ci parla tramite l'**Entity Manipulation Language** (**EML**): un insieme di istruzioni ABAP per leggere, creare, modificare e cancellare istanze di entità, chiamare azioni e salvare. L'EML passa per lo stesso comportamento di Fiori, quindi le tue [validazioni, determinazioni e azioni](./0142-rap-validations-determinations-actions.md) girano chiunque sia a chiamare.

Hai già usato l'EML dentro il behavior pool. Questa lezione lo mostra dall'esterno: una classe, un report o un job di background che lavora con il business object dei viaggi.

## I tipi derivati e i componenti %

L'EML lavora con **tipi derivati**, generati dalla behavior definition. Raramente li dichiari tu, perché lo fanno le dichiarazioni inline, ma devi conoscere i loro componenti speciali:

| Componente | Significato                                                                          |
| ---------- | ------------------------------------------------------------------------------------ |
| `%cid`     | un content ID che scegli tu, per riferirti a un'istanza che non ha ancora una chiave |
| `%cid_ref` | si riferisce al `%cid` di un'altra istanza nella stessa richiesta                    |
| `%tky`     | la chiave transazionale: campi chiave più campi tecnici come `%is_draft`             |
| `%key`     | solo i campi chiave                                                                  |
| `%control` | quali campi sono impostati (`if_abap_behv=>mk-on`); lo riempie `FIELDS ( ... )`      |
| `%target`  | le istanze figlie in una create by association                                       |
| `%param`   | il risultato di un'azione                                                            |

La forma esplicita di un tipo derivato è del tipo `TYPE TABLE FOR CREATE zr_travel\travel`, `TYPE STRUCTURE FOR READ RESULT zr_travel\booking` e così via.

## Creare con MODIFY ENTITIES

```abap
CLASS zcl_travel_eml DEFINITION PUBLIC FINAL CREATE PUBLIC.
  PUBLIC SECTION.
    INTERFACES if_oo_adt_classrun.
ENDCLASS.

CLASS zcl_travel_eml IMPLEMENTATION.
  METHOD if_oo_adt_classrun~main.
    MODIFY ENTITIES OF zr_travel
      ENTITY Travel
        CREATE FIELDS ( CustomerID BeginDate EndDate CurrencyCode Description )
        WITH VALUE #( ( %cid         = 'T1'
                        CustomerID   = '000001'
                        BeginDate    = '20250701'
                        EndDate      = '20250714'
                        CurrencyCode = 'EUR'
                        Description  = 'Vacanze estive' ) )
        CREATE BY \_Booking FIELDS ( CarrierID ConnectionID FlightDate FlightPrice CurrencyCode )
        WITH VALUE #( ( %cid_ref = 'T1'
                        %target  = VALUE #( ( %cid         = 'B1'
                                              CarrierID    = 'LH'
                                              ConnectionID = '0400'
                                              FlightDate   = '20250701'
                                              FlightPrice  = '650.00'
                                              CurrencyCode = 'EUR' ) ) ) )
      MAPPED   DATA(ls_mapped)
      FAILED   DATA(ls_failed)
      REPORTED DATA(ls_reported).

    IF ls_failed IS NOT INITIAL.
      out->write( 'Creazione non riuscita' ).
      RETURN.
    ENDIF.

    COMMIT ENTITIES
      RESPONSE OF zr_travel
      FAILED   DATA(ls_commit_failed)
      REPORTED DATA(ls_commit_reported).

    IF sy-subrc = 0.
      out->write( |Viaggio creato: { ls_mapped-travel[ 1 ]-TravelUUID }| ).
    ELSE.
      LOOP AT ls_commit_reported-travel INTO DATA(ls_message).
        out->write( ls_message-%msg->if_message~get_text( ) ).
      ENDLOOP.
    ENDIF.
  ENDMETHOD.
ENDCLASS.
```

- `FIELDS ( ... ) WITH` elenca i campi che passi e riempie `%control` per te.
- La prenotazione si riferisce al suo viaggio con `%cid_ref = 'T1'`, perché quando scrivi l'istruzione il viaggio non ha ancora un UUID.
- `MAPPED` restituisce le chiavi assegnate dal framework (qui gli UUID managed). `FAILED` elenca le istanze che non è stato possibile elaborare, e `REPORTED` i messaggi.
- Nel database non c'è niente fino a `COMMIT ENTITIES`. È lì che gira la sequenza di salvataggio: determinazioni on save, validazioni e scrittura nel database. Se una validazione fallisce, `sy-subrc` vale `4` e i messaggi sono nelle strutture di `RESPONSE`.

## Leggere, modificare e chiamare azioni

```abap
    DATA(lv_uuid) = ls_mapped-travel[ 1 ]-TravelUUID.

    READ ENTITIES OF zr_travel
      ENTITY Travel
        FIELDS ( TravelID OverallStatus ) WITH VALUE #( ( TravelUUID = lv_uuid ) )
        RESULT DATA(lt_travels)
      ENTITY Travel BY \_Booking
        ALL FIELDS WITH VALUE #( ( TravelUUID = lv_uuid ) )
        RESULT DATA(lt_bookings)
      FAILED DATA(ls_read_failed).

    MODIFY ENTITIES OF zr_travel
      ENTITY Travel
        UPDATE FIELDS ( Description ) WITH VALUE #( ( TravelUUID = lv_uuid  Description = 'Vacanze in famiglia' ) )
        EXECUTE acceptTravel FROM VALUE #( ( TravelUUID = lv_uuid ) )
        RESULT DATA(lt_accepted)
      FAILED DATA(ls_upd_failed)
      REPORTED DATA(ls_upd_reported).

    COMMIT ENTITIES.
```

- `READ ENTITIES ... BY \_Booking` segue un'associazione. `ALL FIELDS` legge tutti i campi.
- `UPDATE FIELDS` cambia solo i campi elencati; gli altri mantengono il loro valore.
- `EXECUTE azione FROM` chiama un'azione, e `RESULT` restituisce quello che l'azione ha dichiarato (`$self`).
- `DELETE FROM VALUE #( ( TravelUUID = lv_uuid ) )` cancella, e con la composizione se ne vanno anche le prenotazioni.

Per una sola entità esiste una forma più corta: `MODIFY ENTITY zr_travel UPDATE FIELDS ( ... ) WITH ...` e `READ ENTITY zr_travel ...`.

> [!WARNING]
> Non usare mai `COMMIT ENTITIES` o `COMMIT WORK` dentro un behavior pool, una determinazione o una validazione: il commit lo fa il framework, e il runtime genera un dump. Fai il commit solo nel codice che **avvia** la transazione: il tuo report, la tua classe o il tuo job.

## Local mode e accesso privilegiato

| Aggiunta            | Dove la usi                            | Effetto                                                                                        |
| ------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `IN LOCAL MODE`     | solo nel behavior pool dello stesso BO | salta i controlli di autorizzazione e di feature control                                       |
| `PRIVILEGED`        | in qualsiasi consumatore               | salta i controlli di autorizzazione, se la behavior definition permette l'accesso privilegiato |
| `ROLLBACK ENTITIES` | nel consumatore                        | scarta tutto ciò che c'è nel buffer transazionale                                              |

`IN LOCAL MODE` non è permesso fuori dall'implementazione del business object. Un consumatore passa sempre per tutti i controlli, ed è proprio quello che vuoi.

## Esercizio

> [!IMPORTANT]
>
> 1. Crea la classe `ZCL_TRAVEL_EML` ed eseguila con `F9` per creare un viaggio con una prenotazione.
> 2. Estendila: leggi il nuovo viaggio, stampa `TravelID` e `OverallStatus`, poi accettalo e stampa di nuovo lo stato.
> 3. Crea un viaggio con la data di fine precedente a quella di inizio. Che cosa contengono `sy-subrc` e `ls_commit_reported` dopo `COMMIT ENTITIES`?

### Soluzione

Dopo il passo 2, `TravelID` ha il numero della determinazione `setTravelID`, e lo stato passa da `O` ad `A`. Al passo 3, `MODIFY ENTITIES` riesce, perché le validazioni girano solo al salvataggio. `COMMIT ENTITIES` imposta `sy-subrc` a `4`, `ls_commit_failed-travel` contiene l'istanza e `ls_commit_reported-travel` il messaggio di `validateDates`.

> [!NOTE]
>
> - L'EML legge e modifica i business object RAP da ABAP, passando per lo stesso comportamento di Fiori.
> - `MODIFY ENTITIES` crea, modifica, cancella ed esegue azioni; `READ ENTITIES` legge e segue le associazioni.
> - Usa `%cid` e `%cid_ref` per le istanze che non hanno ancora una chiave; `MAPPED`, `FAILED` e `REPORTED` restituiscono chiavi, errori e messaggi.
> - Le modifiche restano nel buffer transazionale fino a `COMMIT ENTITIES`, che esegue la sequenza di salvataggio.
> - `IN LOCAL MODE` solo dentro il behavior pool; non fare mai il commit nel codice del business object.
